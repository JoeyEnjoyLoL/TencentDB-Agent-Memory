P0-1：重复投递没有幂等键
worker 对 5xx/网络错误保留文件重试（worker.ts:190），这是对的。问题在于「网关已处理、响应丢了」这一类重试会产生重复 L0，而 Core 的两层去重在这条路径上都是失效的：

去重层	依赖	Cursor 路径实际情况
位置切片
originalUserMessageCount
CaptureRequest 里没有这个字段，网关也没传（server.ts:402）
时间戳游标
messages[].timestamp
adapter 只发 3 个字段（worker.ts:165），网关补的 messages 无 timestamp → 提取时赋 Date.now()，恒大于游标
第二点是 l0-recorder.ts:155 注释自己写明的行为。另外 unlink 失败被静默吞掉（worker.ts:174），也会导致下一轮重发。

建议：pending 事件里已经有 at_ms，把 messages: [{role,content,timestamp: at_ms}] 一起发出去，时间戳游标层立刻恢复生效；顺带给 unlink 失败补一条 log。

500 / 网络错

POST /session/end

最后几轮未进 L0且 sessionEnd 不重试, 永久丢失
/session/end 会真的触发 flush（server.ts:475），而 sessionEndKey 只存在于命令行参数里，失败只记一行日志（worker.ts:203）——测试甚至把这点固化成了预期行为（worker.test.ts:214「失败后不写持久状态」）。

建议：capture 有 retained 时跳过 /session/end；并把 sessionEndKey 落成 pending 目录里的一个 marker 文件，让下一次 worker 接着重试。

P0-3：防护字段在唯一的采集事件上不存在

hooks.ts
Lines 20-24
function isTopLevelInteractive(payload: HookPayload): boolean {
  if (payload.is_background_agent === true) return false;
  if (text(payload.parent_conversation_id)) return false;

他们自己的 spike 报告字段矩阵写着：before / after / stop —— 无 is_background_agent、parent_conversation_id（docs/spike/2026-07-30-linux-cursor-3.12.30.md:111），且真·Background Agent 采到 0 条样本。采集只发生在 stop，所以这个函数对采集路径恒返回 true，后台 Agent 的轮次会照样进用户记忆。hooks.test.ts:178 用 beforeSubmitPrompt/afterAgentResponse 构造的测试制造了「已防护」的假象——而这两个事件 installer 根本没注册（installer.ts:15）。

建议：在 sessionStart（该事件确实带 is_background_agent）把判定结果落一个 per-conversation marker，stop 时查 marker；同时删掉 beforeSubmitPrompt/afterAgentResponse 这两段死代码。

#4：proper-lockfile 在 compromise 时置 lock.released = true（lockfile.js:187），随后 release() 走 ERELEASED 分支（:255）。finally { await release() } 无 catch，会把 try 块里的真实异常替换成 ERELEASED；detached 进程 stdio 是 ignore，stderr 直接进黑洞。加 .catch() 并落日志即可。
